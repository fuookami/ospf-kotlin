# Network Structure

[简体中文](README_ch.md) | [Framework guide](../README.md)

Public API: `NetworkStructureProblem<V> / NetworkStructureContext<V>`. The immutable problem contains a `NetworkDesignProblem<V>`; each context creates its own `NetworkDesignContext<V>` using the supplied value adapter.

The context builds a rooted directed arborescence over explicitly allowed root, terminal and optional Steiner nodes. Every active non-root node has exactly one selected incoming parent arc, the root has none, and bounded depth constraints explicitly exclude directed cycles. Depth is bounded by the number of allowed tree nodes minus one, so the acyclicity linking constant is finite and derived from the graph. Terminals are mandatory; Steiner nodes are optional. Arc identity is `NetworkArcId`, so parallel arcs remain independent choices; self-loops are fixed off. Arc direction is never reversed or inferred from cost, and connectivity does not rely on a low-cost tree assumption.

Tree arcs are linked to the corresponding design service availability and both endpoint facility activations. Active tree facilities must be open. A facility/service without an optional construction decision is treated as already available by the design context. Facility partition requests use an explicit eligible-facility set, exactly one owner by default (optionally none), and optional per-facility assignment-count quotas. These assignments are separate binary coverage decisions; they are not inferred from or coupled to commodity demand.

Registration shares only the design construction component (facility/service variables and budget) and deliberately does not register nominal commodity flow. By default it registers a separate objective that minimizes `constructionCost`; pass `minimizeCost = false` when embedding this context into a model whose objective is composed elsewhere. The expression remains exposed for caller composition. Unknown or duplicate references and invalid quota bounds are rejected during registration; valid but disconnected topology, a required partition with no eligible facility, or a minimum quota above eligible coverage is represented by model constraints and must be reported as model infeasibility by the solver, not as registration failure. Domain construction values remain `V : RealNumber<V>` and `Quantity<V>` through the design adapter; solver symbols are `Flt64`. A context is single-use: after any registration failure, discard the context and partially modified model. The API has no solver-specific application or test dependency.
